## 3 先盘点再导出

以下命令均在终端逐块执行。使用可用的 Python 3；`python3` 找不到时指定你的 Python 路径。准备脚本只用标准库，不启动模型、浏览器或产品服务。后续示例变量只用于当前终端，不覆盖系统变量。

```bash
export ARC_OLD="$HOME/Desktop/research/FYP/arc-bench"
export ARC_NEW="$HOME/Desktop/research/FYP_new/arc-bench"
export ARC_GUIDE="$ARC_OLD/docs/fork-migration-handoff-2026-10-21"
export ARC_STAGE="$HOME/Desktop/research/arc-handoff-20261021"
```

先确认仓库身份和工作区。旧仓库存在未提交实验是正常现状，不应为了获得“干净状态”而 reset 或删除。新仓库若已有修改，先审阅并保存，不覆盖它们。

```bash
git -C "$ARC_OLD" status --short
git -C "$ARC_NEW" status --short
git -C "$ARC_NEW" remote -v
git -C "$ARC_NEW" rev-parse HEAD
```

确认远端为目标 fork，保存原状态，然后在新仓库创建迁移分支。若 main 已推进，记录实际基线；不要退回旧提交覆盖新工作。

```bash
git -C "$ARC_NEW" switch -c migration/test-fidelity-handoff
python3 "$ARC_GUIDE/prepare_handoff.py" inventory \
  --source "$ARC_OLD" --out "${ARC_STAGE}-inventory"
```

查看 `${ARC_STAGE}-inventory/manifest.json` 的 files、exclusions、总大小和 source_head。清单来自当前工作区字节，包含未提交内容，不只是旧 HEAD。检查缺失项、被排除的链接、任何私密路径以及大文件。输出目录必须是新的空路径，脚本遇到已存在目录会退出，不会覆盖。

确认范围后执行导出。下面只写入暂存目录，不修改两个仓库。

```bash

  --source "$ARC_OLD" --out "$ARC_STAGE"
python3 "$ARC_GUIDE/prepare_handoff.py" verify --out "$ARC_STAGE"
```

应得到 `mismatch_or_missing: []`。这证明暂存文件与清单一致，不证明契约、自测入口或路径可移植问题已经解决。若盘点与导出之间旧材料发生变化，比较两份清单并解释差异；不要混用不同冻结状态。

## 7 核验迁移结果

### 7.1 先重算历史结果

评分重算只需已保存的 JSONL、材料 manifest 和标签，不需要启动服务或模型。以下命令从新仓库执行，并把结果写入新目录。重复运行时使用新的输出目录名。

```bash
cd "$ARC_NEW"
export ARC_V2="experiments/benchmark-fidelity-v2"
mkdir -p runs-local/migration-score
python3 "$ARC_V2/tools/score_v2.py" \
  --runs "$ARC_V2/runs/regression/regression-k3.jsonl" \
  --set old-dev old-sealed --k 3 --methods B D \
  --out runs-local/migration-score/regression.json
```

分别对 new-dev 子集、acceptance K3 和 acceptance K10 重算。new-dev 实际存放在 regression 运行文件中，使用 `--set new-dev`；acceptance 分别读 `runs/acceptance/acceptance-k3.jsonl` 和 `runs/acceptance-k10/acceptance-k10.jsonl`，不要将两者重复编号拼成一次 K13。前两者用 `--methods B D`，K10 用 `--methods D`。H 只跑了三个已知正确父版本及其六个缺陷，不能以完整旧回归分母把它未运行的单位计作失败。

| 数据集 | B 的 CAR 与 EDR | D 的 CAR 与 EDR |
| --- | --- | --- |
| 旧回归 36 单位 | 9/12 与 18/24 | 12/12 与 24/24 |
| 新开发 18 单位 | 4/6 与 8/12 | 6/6 与 12/12 |
| 验收 18 单位 K3 | 4/6 与 8/12 | 6/6 与 12/12 |
| 验收 D 单独 K10 | 未运行 | 6/6 与 12/12 |

注意旧回归的单位筛选在 scorer 中以 set/origin_split 为准。上面的命令用 old-dev 和 old-sealed 取得 12/24 的旧回归；`--set regression` 会包括新开发集，得到 18/36 的合并分母。不要因路径名叫 regression 就把两个数据集混淆。表中 D 的额外 EDR 来自正确父版本恢复；共同通过父版本的缺陷检出能力没有增加。

### 7.2 验证生产测试和产品负例

先让生产库的 20 个评测器夹具全部通过，再用新路径适配入口运行正确父版本与各自目标缺陷，至少覆盖 v2 的三个已知 P1 绑定失败案例及三条已迁移需求。每个需求级单位必须跑齐两个场景，检查目标义务确实到达；正确版本全过、缺陷在预期业务义务处失败才算有效。

本次迁移代码未改时，可先做单次迁移冒烟。若补契约时改了判据，或改动驱动、观察器、oracle、标题映射和分类逻辑，重新跑受影响配对及原回归；有行为变化再扩大到完整 72 单位并执行所需重复协议。不要为了迁移机械重跑 36 次模型修订，也不需要重新训练或换框架。

此前 10 月 21 日审计中，20 个自测通过，单次冒烟的四个正确单位通过、八个缺陷有效拒绝。这些可以作迁移基线，但不能代替你在新入口和新工作区的验证。

### 7.3 用干净 checkout 证明交接独立

完成本地提交后，从新仓库创建一个新的临时 clone，按仓库 README 安装依赖。暂时不要设置 ARC_OLD 或指向旧目录的 NODE_PATH/PATH，记录全部命令；无需重命名或删除旧工作区。核对解析后的材料路径全部位于这个新 clone，依赖均在声明位置，没有旧目录符号链接。

干净 checkout 至少应能读取报告及证据、重算历史指标、跑 20 自测、构建一个正确父版本及其缺陷，并运行生产 D 配对检查。若材料使用 Release 附件，此时实际下载和验证 SHA256。缺任一环节，迁移状态仍为未完成。
