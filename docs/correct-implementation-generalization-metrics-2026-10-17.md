# ARC-Bench：正确实现的判定与泛化性指标

日期：2026-10-17。性质：文献调研与建议协议，没有新增应用运行实验。上游背景固定为 `code-philia/arc-bench@ace00e28a0ae950f4bf20c138de1ae18b2285513`；本地旧实验不作为当前上游表现。

核心建议：先建立独立的、需求级的正确性标注集，再评估冻结测试对留出正确实现的接受能力。CAR 是接受能力的经验统计，不能自行证明被接受的软件正确。以下指标名称和协议是本项目建议，不宣称来自某篇论文的统一标准。

## 1. 文献发现及可迁移范围

### Barr et al., The Oracle Problem in Software Testing: A Survey, TSE 2015

- 依据：§2 的 oracle 定义、§2.3、§4 和 §7。
- 文献讨论如何区分期望行为与错误行为，以及规格、模型、派生 oracle 和人工判断。理想 ground truth 是概念上的参照，实际 oracle 通常不完备。
- 对本任务的启示：必须区分需求语义、参考判定和待评测的 Playwright 测试；不能把其中任意一套测试的通过直接当成全程序正确。
- [作者公开全文](https://philmcminn.com/publications/barr2015.pdf)

### Liu et al., Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation, NeurIPS 2023 / EvalPlus

- 依据：§2、§3 的 ground-truth 检查。
- 论文通过增加输入及差分测试加强代码评测，并报告在 HumanEval 原参考实现中发现 18 个缺陷，包含边界、逻辑和性能问题。
- 启示：reference implementation 也需要核对；多个实现发生分歧有诊断价值，但多数一致不能自动成为真值。
- 适用边界：函数输出通常比 Web 多种合法交互结果更容易比较。Web 应比较需求相关的业务状态，不能要求 DOM 或 URL 与参考实现逐字一致。
- [作者公开全文](https://kristoff-starling.github.io/pubs/neurips2023_evalplus.pdf)

### Lu et al., WebGen-Bench: Evaluating LLMs on Generating Interactive and Functional Websites from Scratch, 2025

- 本次核对 arXiv v1 的 §3.2、§4.3；不同修订版的数字可能不同。
- 测试条目采用“操作＋期望结果”，两名博士生独立审阅和修订条目。校验自动评测时，三名人工测试者独立标注，分歧交由第四人复核。
- 自动执行使用 UI agent，并返回 YES / PARTIAL / NO；论文报告自动与人工判定的一致率。
- 启示：可复用需求级操作与结果条目，以及独立人工执行和裁定流程。
- 边界：总体一致率可能掩盖对正确实现的误拒；PARTIAL 不应直接作为“正确实现”进入 ARC-Bench 的正样本集。
- [全文 §3.2、§4.3](https://arxiv.org/html/2505.03733v1)

### Meng et al., WebRISE: Requirement-Induced State Evaluation for MLLM-Generated Web Artifacts, 2026 预印本

- 依据：§4、附录 A.3、B。
- 将需求表达为可观察状态、用户意图转换及 DOM/视觉断言；浏览器 agent 根据当前页面自适应执行。保存轨迹、DOM 日志和截图作为判断证据。
- 人工校验分别考察需求到交互契约的构建和功能判定，报告 agreement 与 Cohen's kappa；其 agent 功能评价与人工多数判断的一致率为 0.84，kappa 为 0.74。
- 启示：规格是否正确与执行结果是否正确需要分别核对；自动 judge 仍需校准。
- 边界：论文还评价隐含产品约束。ARC-Bench 的硬性要求需有冻结规格依据，不能直接引入主观“产品应该如此”的条件。
- [全文及附录 A.3](https://arxiv.org/html/2606.03220v1)

### Liu et al., IWC-Bench: Evaluating Web Application Generation from a Software Testing Perspective, 2026 预印本

- 依据：§1、§3.3、§4.4、§5.3、§6。
- 区分运行探索与评分，指出定位/交互失败可能与产品缺陷混淆，要求需求条目的判断引用运行证据。
- 其 85.3% 是 197 个经验证会话上的人工偏好配对一致率，不是“正确实现被接受率”，也不是单条功能正确性的准确率。
- 启示：需要记录未到达、已到达但结果错误、证据不足等情况。
- 边界：论文任务范围为前端任务；其验证不能直接证明 ARC-Bench 完整后端业务的正确性。
- [全文](https://arxiv.org/html/2609.15387v1)

### Shin et al., Assessing Evaluation Metrics for Neural Test Oracle Generation, TSE 2024

- 研究发现文本相似度指标与运行时测试充分性指标之间没有显著相关性。
- 启示：不能通过测试代码与参考测试相似、断言数量更多，来认定测试更正确或更能泛化。论文所考察的代码覆盖率与 mutation score 也不直接构成 Web 正确实现的语义标签。
- [作者公开全文](https://www.eecs.yorku.ca/~wangsong/papers/tse24.pdf)

### Liu et al., Towards More Realistic Evaluation for Neural Test Oracle Generation, ISSTA 2023

- 论文强调 bug-finding 场景中告警 precision 对开发者检查成本的重要性，并指出从 bug-fixed 版本构造输入可能引入不现实的信息优势。
- 启示：指标必须对应使用目的，且训练/改进与最终评测信息需要隔离。
- 边界：不能据此说“所有 false positive rate 都无用”。本任务直接关注正确实现是否被误拒，条件于正确实现的接受率/拒绝率仍有明确意义；precision 受正负样本组成影响。
- [全文](https://arxiv.org/pdf/2305.17047)

### TOGLL: Correct and Strong Test Oracle Generation with LLMs, 2024

- 论文分别评价 oracle 的可执行正确性与 mutation 检出强度。
- 启示：让测试在某个已有版本上通过，与发现需求错误，是两个维度。
- 边界：其对已有 Java 项目执行测试的验证方式，不足以直接认证从零生成的 Web 应用满足自然语言需求。
- [全文 §III-B、III-D](https://arxiv.org/html/2405.03786v1)

## 2. “正确”的评价单位

使用 `(需求/场景 r, 应用实现 p, 环境 e)`，不先给整个应用一个无条件正确标签。

一条需求包含多个场景时，应逐场景标注；只有在预先声明的检查范围内，全部必需场景和义务均满足，才能汇总为该需求已验证满足。单条成功轨迹只证明相应路径和输入上的行为。

输出三值参考标签：

- `SATISFIED`：规定前置条件已成立，声明范围内的必需义务都有正面运行证据。
- `VIOLATED`：至少一项明确义务有可复现反例。
- `UNDETERMINED`：需求歧义、环境不成立、证据不足、操作未完成或裁定未解决。

这里的 SATISFIED 表示“在声明的检查范围内经验证满足”，不是形式化证明所有输入下的整个程序正确。

## 3. 独立参考判定协议

1. 冻结需求版本，列出原文出处、前置条件、合法输入范围、用户动作、目标对象、必要后置条件、保持条件、允许变化和歧义。
2. 建立公开义务清单，由人工审核其完整性和来源；不从候选 Playwright 测试反推需求。
3. 通过人工浏览器操作或独立执行器收集运行证据。必要时为该实现编写适配操作，但只能用于参考证据收集，不能悄悄用于提高被评测测试的成绩。
4. 在干净且固定的初始状态下执行规定场景；按需求覆盖关键输入、目标对象和入口，保存动作、输入、对象身份、前后状态及重载后的状态。
5. 两位审阅者独立按同一义务清单给出三值标签，尽量隐藏生成模型、测试版本和候选测试的结果；争议由第三人裁定或保留未决。小规模试验若仅有一人审阅，披露这一限制。
6. 用冻结记录建立正样本集，再运行候选测试。不能只挑原始 benchmark 已通过的实现。

参考证据可以由 Playwright 收集，工具相同并不等于循环论证。关键是义务来自独立审核的规格，适配器与候选测试隔离，标签不依赖候选测试成败，且保留人工复核。另写一份未经验证的同类测试并不足够。

对关键视觉义务保留截图和人工/VLM 核验；保存、筛选、删除、对象一致性等优先用轨迹与业务结果核验。代码或数据库状态可作辅助证据，但 UI 不可用时，后台记录不能替代用户可用性的要求。

## 5. 指标：先标注正确性，再衡量泛化

对每项需求 r，令 C_r 为独立判定为 SATISFIED 的留出实现集合，B_r 为冻结候选测试。不存在正样本的需求不能得到 CAR=0 或 CAR=1，应报无可估计样本。

### 5.1 主指标：正确实现接受率 CAR

`CAR_r = Σ[p∈C_r] accepted(B_r,p) / |C_r|`

`Macro-CAR = mean_r(CAR_r)`，同时报告原始分子/分母。

accepted 的具体执行规则需要预先冻结。例如每个单元在重置环境下无自动重试地执行 K=3 次，三次全部通过记 1；其他记 0。此时名称应写成“3 次均通过的正确实现接受率”，避免把 K 的变化当作方法收益。

该指标将定位不兼容、错误额外断言以及候选测试自身失效都视为无法接受已验证正确的实现。失败原因另分为定位/操作、语义断言、偶发翻转、测试工具错误。外部环境异常需要重跑或保留未决并披露，不能伪称已测成功或静默删除。

它是端到端操作性指标。只有在所有情况都被二分为通过/拒绝时，误拒率才等于 1-CAR；如果单列不稳定、无判定或工具错误，应报告各类比例，称 1-CAR 为“未稳定接受比例”。

### 5.2 泛化的成立依赖评测集划分

- 只在改进时见过的实现上计算：适配表现。
- 在留出的实现实例上计算：对这些新实现的迁移。
- 留出整个技术栈或组件家族：对该留出技术栈/家族的泛化。
- 同源代码、保义改写家族必须整体分组，避免近重复泄漏。

分别报告各栈/布局/组件类型的 CAR。最低分组 CAR 可作为补充，但要给样本量和不确定性，不能把只有一两个样本的极端值解释为稳定能力。

同一业务的不同正确实现可以产生多个合法结果；用预先定义的业务投影比较，例如对象身份和保存内容，而不要求完整 DOM、URL、内部 API 或数据库表示一致。

### 5.3 配对的等价实现接受

对经独立验证的正确实现对 `(p,p')`，报告二者都被接受的比例：

`PairAccept = #(B(p)=PASS 且 B(p')=PASS) / #合法正确实现对`

另列 pass→fail、fail→pass、pass→pass、fail→fail。仅统计 verdict 一致性会把“两个都拒绝”误当成泛化成功。配对变换指标用于定位敏感因素，不能替代独立跨栈实现上的 CAR。

### 5.4 必须保留的反作弊约束

在预先确认有效的需求违反集上统计有效检出率：对应正确版本通过，错误版本因目标义务失败。不能把无条件失败、语法错误或无关定位失败算作检出。

CAR=100% 可以由空测试得到，所以任何“泛化改善”结论都要同时报告有效检出能力及功能检查范围。覆盖率、断言数量、使用 getByRole 的比例仅能作诊断，不能作为正确性或泛化性的替代指标。

## 6. 如果用 LLM 判断正确实现，还要评价 judge 本身

在独立人工裁定集上，以“满足需求”为正类。以下 precision/recall 在 H 可裁定的子集内计算；decision coverage 在全部评价单元上计算。H 表示人工参考标签，J 表示 judge 标签。

- `Correct-label precision = #(J=SATISFIED 且 H=SATISFIED) / #(J=SATISFIED)`：模型宣布正确的实现中多少得到人工支持，决定正样本集的可信度。
- `Correct-label recall = #(J=SATISFIED 且 H=SATISFIED) / #(H=SATISFIED)`：模型漏掉多少正确实现。
- `Decision coverage = #(J∈{SATISFIED,VIOLATED}) / #全部评价单元`：报告模型弃权范围。
- 报告完整混淆表、人工未决数、逐技术栈表现、人工之间一致率，以及适用时的 Cohen's kappa。kappa 反映一致性，不等于真值或证明。

上面 precision/recall 的有效语义比较使用 H 可裁定的部分；如果 J 宣布正确而 H 未决，应列为未确认正标签，不能隐去后宣称整体 precision 很高。若需要严格正样本池，可只接纳人工确认满足的条目。

置信度分数、多个 LLM 投票和 judge 自称确定都不是独立真值。若按分数阈值弃权，应在验证集固定阈值，并在留出集同时报告 precision 与 coverage。

## 7. 一个具体判定示例

需求：输入标题和内容，点击 Close 后自动保存；刷新后仍保留。

参考判定的必需证据应覆盖：输入的是新创建的独特对象；使用规定的 Close 入口；保存标题和内容对应输入；刷新后能重新找到同一对象及内容。若规格要求恰好一条，则也核对重复数量。额外的服务重启持久化不在“刷新后保留”中自动成立。

- 独立操作已确认上述结果，候选测试因额外 URL 断言失败：该目标需求的误拒证据。
- Close 后丢失输入：需求违反。
- agent 未找到 Close，人工操作尚未完成：未决，不能直接标成业务缺陷。
- 只有数据库记录而 UI 无法操作：不能以后台记录证明 UI 需求满足。
- 页面只有同名旧笔记：不能证明本次创建成功。

## 8. 建议最先开展的工作

先做一个成本可控的正确性标注试验，例如 6 条明确需求、每条 3 个独立实现，共 18 个需求—实现单元。这是可行性试验规模，不足以证明普遍泛化。

1. 先冻结义务和标签协议；实现者只看公开需求。
2. 独立采集并复核证据，不预先假设所有生成实现都正确。
3. 报告满足/违反/未决数量、人工分歧与用时。
4. 在经确认正确的留出单元上评估原始 benchmark 的 CAR 及原因。
5. 正样本足够且规则可复用后，再开展多轮测试改进。

正式分析应对需求/应用/同源家族聚类处理，重复运行不当作独立实现扩大样本量。先报告计数和分组差异；更大规模后再给适当的区间和配对比较。

当前没有已有实验证据证明上述自动 judge 或多轮改进在 ARC-Bench 有效；此文给出可验证的设计，后续必须通过实际执行检验。
