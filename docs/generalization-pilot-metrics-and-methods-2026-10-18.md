# ARC-Bench 泛化性：初步指标、试验方案与改进方法

日期：2026-10-18。状态：建议协议，尚未执行本轮实验。本文的规模、门槛、方法分组属于建议，不代表已经确认的老师要求或已有实验结果。

本次直接核对 GitHub 上游 main，固定为 `c583968dcde891cf58ad3b54a03c757affc44c54`。本地旧实验不代表此版本的表现。

目标：在需求含义和公开交互约定保持一致的条件下，提高冻结测试对未参与修订的正确实现的接受能力，同时保留对明确需求缺陷的检出能力。

第一轮推荐路线：独立确认正负样本 → 运行上游测试 → 基于开发样本执行反馈进行最多三轮离线测试修订 → 冻结测试 → 在留出实现上评价。LLM 用于诊断与修订，最终产品仍为可独立运行的 Playwright 测试。

## 1. 正确性标签先于指标

评价单位为“需求 r × 实现 p × 固定运行条件”。测试套件包含选定需求的全部场景；若只能做其中一个场景，需预先更改评价单位，不能用单场景结果宣称整条需求满足。

先根据冻结规格提取前置条件、合法输入、指定入口、目标对象、必需后置条件及允许变化。对每个实现收集独立运行证据，给出：

- SATISFIED：声明范围内的必需义务均得到支持；必要前置功能可用。
- VIOLATED：明确义务有可复现违反。
- UNDETERMINED：规格歧义、环境异常、证据不足或裁定未完成。

初期可以一人逐项操作并记录证据，第二人复核全部争议与关键场景，披露审阅覆盖；资源允许时两人独立标注。候选测试成败不用于定义参考标签。

参考实现也需要验证。生成出的实现不自动进入正样本集。正确性结论限于检查范围，不是整个应用无缺陷的证明。

当前上游已经公开许多 role/name 约定。合规正样本需要满足这些约定；要放宽约定，应另建冻结规格版本，并将其作为独立实验因素。单纯把 button 改成没有规定角色的可点击 div，不能默认是合法变化。

## 2. 最小指标集

以下缩写是本方案的操作性定义，并非声称沿用某篇论文的标准指标。`@3` 表示独立重置执行三次且全部满足条件，不是“尝试三次有一次成功”的 pass@k。

| 指标 | 计算方式 | 用途 |
|---|---|---|
| CAR@3：正确实现稳定接受率 | 独立确认正确的单元中，重置后执行 3 次均通过的数量 / 固定正确单元总数 | 主要泛化指标，最终在留出实现上计算 |
| EDR@3：配对有效缺陷检出率 | 对应正确版本 3 次通过、缺陷版本 3 次因目标义务失败的配对数 / 固定有效缺陷配对数 | 防止通过删除检查提高 CAR |
| Flaky@3：不稳定率 | 完成重复运行的单元中同时出现 PASS 与 FAIL 的数量 / 完成重复运行的单元数 | 运行稳定性，不能单独表示正确性 |
| 成本 | 修订调用数、token/费用、修订耗时、最终执行耗时 | 判断改进是否值得，另列而不混成总分 |

令 C_r 为固定的正确单元集合、M_r 为预先验证有效的缺陷配对集合：

`CAR_r@3 = sum(p in C_r, all_three_pass(T_r,p)) / |C_r|`

`EDR_r@3 = sum((p,m) in M_r, all_three_pass(T_r,p) AND all_three_target_fail(T_r,m)) / |M_r|`

逐需求给出 k/n，再对需求取平均，并按应用和实现族展示。零有效样本记不可估计。三次执行是重复测量，不能当作三个独立实现。

规则：

1. 固定正负样本分母，不因某版测试无法运行或无法接受正确版本而筛掉样本。
2. 候选测试语法错误、定位不兼容、额外断言等使已知正确实现无法被接受，CAR 记 0，原因另列。
3. 外部环境失败先按统一协议修复重跑；仍未决则披露计划数、完成数与未决数。给完成案例结果和以计划分母计算的保守下界，不能把未知伪装成已确认业务失败或静默删除。
4. EDR 分母不随 CAR 改变。CAR 修复会使一部分有效检出变得可计，这是端到端指标的含义；同时报告正确版本通过条件及每个负例的结果。
5. 失败归因依据义务和轨迹。若故意删除需求要求的 Close 入口，找不到 Close 可以是目标检出；若在不相关登录环节超时，则不是目标检出。
6. 始终失败也可能 Flaky=0，因此不稳定率只能配合 CAR、EDR 阅读。
7. 使用 PASS / ASSERTION_FAIL / ADAPTATION_FAIL / TEST_ERROR / INFRA_UNRESOLVED 保存原始结果。PASS/FAIL 翻转用于 Flaky；TEST_ERROR、INFRA_UNRESOLVED 的数量及状态翻转另列。

初期不必单设综合 reward。正确实现误拒原因可另列为定位、动作、额外语义限制、时序/状态、执行工具错误。在存在未决和工具错误时，不把 `1-CAR@3` 全部称为语义误拒率。

## 3. 最初三个需求候选

以下根据当前上游行为类型选择，尚未确认它们存在泛化失败。

| 需求 | 独立参考判定重点 | 两类负例候选 |
|---|---|---|
| Keep REQ-2.2 创建并自动保存 | Close 触发保存；唯一标题和多行内容正确；刷新后保留 | Close 丢弃输入；只保存在刷新后丢失的内存状态 |
| Keep REQ-4.1 搜索和建议筛选 | 标题/内容匹配、排除不匹配对象、高亮、标签筛选及清空恢复 | 只匹配标题；建议标签筛选保留未标记笔记 |
| BookStack REQ-6.4 读取页面及重开编辑器 | 打开所选对象、正确正文、编辑器预填正确标题与正文 | 打开错误对象；预填错误/空正文 |

BookStack 的“总打开第一篇”需要至少两个可区分页面并选择非第一篇，独立探针确认缺陷确实生效；否则不能算有效负例。

必要前置流程需实现并核对。例如 BookStack 测试通过创建书籍和页面准备数据，不能只做一个可直接访问的孤立阅读页面。目标功能可构成应用的纵向切片，不要求其他无关功能完整，但不能用绕过前置业务的桩冒充满足需求。

一个静态风险线索：REQ-6.4 规格以有名称的 textbox 描述编辑字段，而对应测试及 createPage helper 通过固定 placeholder 定位。若完整需求和参考资料没有要求该 placeholder，只有正确 label 的实现可能被拒。这是待运行确认的候选，不是已确认误拒。

### 最小启动检查

先只做 BookStack REQ-6.4 的两个合规实现和一个有效缺陷版本，确认上述风险和参考判定流程可执行。没有确认误拒时照实记录，再按预定的另外两个需求继续；不能为了制造误拒而改写需求。

## 4. 泛化试验材料与划分

完整初试目标：3 条需求，每条 4 个独立实现，2 个用于开发、2 个留出。每个正确实现准备 2 个有效缺陷版本。

| 集合 | 正确需求—实现单元 | 缺陷单元 | 是否提供改进反馈 |
|---|---:|---:|---|
| 开发集：实现族 A、B | 6 | 12 | 是 |
| 留出集：实现族 C、D | 6 | 12 | 否 |
| 总计 | 12 | 24 | 共 36 个运行目标 |

这是核验后的目标数量；生成材料未满足规格时需先修复并重新独立核验，未决材料不得凑数。按应用复用实现：Keep 每套实现支持两条目标需求，BookStack 支持一条及其前置流程，所以四族对应最多八套小型应用，不是十二套完整应用。

实现族示例（待构建前冻结具体选型）：

- A：React 的独立实现，用原生控件；开发。
- B：Vue 的独立实现，不同 DOM 和布局；开发。
- C：React 的另一独立代码实现及不同组件表达；留出，考察实现/组件变化。
- D：Svelte 或原生浏览器实现；留出，考察未见前端栈。

这些只是选型示例，不默认任意组件变化都满足公开约定。后端栈先固定可降低成本；此设计只能支持前端实现泛化，后端泛化另做留出，不能将其扩大为任意全栈技术都已验证。

同源代码、派生合法变体和缺陷版本随根实现整体划分。实现者只依据公开需求构建产品，避免阅读候选测试后按其隐含假设修改产品。记录人工构建、独立生成、既有实现等来源。

变化维度至少登记：

| 维度 | 候选合法变化 | 范围约束 |
|---|---|---|
| DOM 与布局 | 包装层、卡片/列表、CSS 类名 | 保留公开语义、对象身份、可见性和必要交互 |
| 字段标注 | label 或 aria-label，必要时不同编辑控件 | 保留要求的名称和可操作性；检查是否另有 placeholder/控件类型约定 |
| 导航 | 内部路由、SPA/整页导航 | 保留需求规定的入口和结果；不能改明确规定的路径 |
| 异步时序 | 预算内合理的渲染或存储延迟 | 只用于另列鲁棒性压力测试；不改变功能或性能义务 |

多个因素同时变化可以测试整体迁移，不能单独归因于某技术栈。定位原因时再对单因素合法改写作配对检查。

## 5. 最小方法对照

| 组别 | 流程 |
|---|---|
| M0 原始 | 冻结当前上游测试和 helpers |
| M1 单轮 | 同一模型读取需求、原测试、冻结义务清单和原测试在开发集的报告，修订一次 |
| M2 多轮执行反馈 | 首轮输入与 M1 相同；之后接收新候选在开发正负实现上的结果，最多修订三轮 |

M1、M2 各做两次独立生成重复。原始 M0 不重复生成。固定模型版本、可读资料、工具、超时、运行环境和每次调用预算，实际用量完整记录。初试中 M2 使用更多修订预算，结论限于流程比较；不能把收益全部归因于反馈。

如果 M2 有收益，再补两个对照：

- M3：相同轮数的纯文本自我审查，去掉新增执行反馈，检验运行证据的贡献。
- M4：同等总生成/执行预算下独立生成多个单轮候选，按相同开发规则选优，检验迭代是否优于多采样。

可再加低成本人工修改版，判断 LLM 是否主要重现简单工程修复。

允许修改定位、对象作用域、动作适配、等待、测试数据和断言实现。冻结的是需求义务，原测试中无依据的断言可以修正；不能把原错误断言也冻结成不可改变。

禁止删除已登记场景、跳过测试、吞掉失败、硬编码开发样例答案、用 API/脚本直接制造应由用户动作产生的结果，或修改产品来迁就测试。检查这些规则不能只看断言数量，仍需行为证据和负例。

## 6. 多轮反馈与候选选择

每轮：生成测试补丁 → 编译/执行开发集 → 保存证据与结果 → 反馈问题 → 提交下一候选。

给模型的反馈包包含：

```text
需求版本、需求/场景 ID、义务原文
实现参考标签、初始数据与环境
失败步骤、目标对象和动作
候选元素及作用域、操作前后 DOM/无障碍树摘要
期望结果、实际结果、目标缺陷是否已显现
不确定性、当前测试补丁
```

不发送留出源码、DOM、截图、执行成绩或人工定位提示。离线冻结脚本路线的最终执行不调用 LLM。运行时自适应路线另列，可读取留出页面的当前 DOM，但策略与预算需事先冻结，不能读取标签或为某留出实现人工修订策略。

初步开发候选选择规则：

1. 义务保留、测试可执行、无绕过行为。
2. 已通过的正确开发单元不能退化。
3. 已检出的开发负例不能变为存活；按负例逐项保护，不能只看汇总检出数。
4. 满足上述条件时优先提高 CAR，再提高 EDR；并列时保留较早/更低成本的版本。
5. 不合格候选保留日志但不替换当前版本；到达三轮上限后交付最后接受的版本。没有改进则返回原版并记录无收益，不能删除该生成重复。

这些门槛属于首轮保守策略，不代表理论最优搜索。小样本上没有退化也不能证明所有实现上没有副作用。

## 7. 执行预算与成功判据

全部方法使用同一冻结执行协议：浏览器版本、locale、时间、数据重置、工作进程数、自动重试策略及整例超时一致。初试使用单 worker、retries=0，每个目标独立重置运行三次。明确区分三次独立评估与失败后重试。

预检若发现上游默认时间预算与所选义务不匹配，应在方法比较前统一设定足够的评估预算，保留原配置下诊断；不能只给 M2 更长等待时间来宣称泛化改善。

留出集 18 个运行目标 × 3 次 = 每套候选测试 54 次需求级执行。M0 一套、M1 两套、M2 两套，共 270 次需求级执行；一条需求可能包含多个 Playwright case。该数量不包含样本认证、开发循环、基础设施重跑或后续消融。

最终输出逐需求、逐实现族、逐生成重复的 CAR/EDR/Flaky 与计数；不以最优生成重复替代整体表现。记录修改前后恢复的正确实现，以及新拒绝的正确实现。

继续研究的初步条件：留出正确接受出现可复核改善；固定缺陷集无新退化，特别是保存、对象绑定等关键负例；没有新增脚本不可用或不稳定问题；成本可接受。若只开发集改善，记录为适配/过拟合风险；若 CAR 升而 EDR 降，记录为判定放松；若原始留出 CAR 已满分，则这批样本没有展示改善空间。

最终留出结果只在方法、轮数、候选选择规则冻结后打开。若用这些结果再修改方法，原留出集转为开发资料，需要新留出材料。

## 8. 改进泛化性的六个机制假设

| 方法 | 具体机制 | 硬条件怎样保留 | 优先级与风险 |
|---|---|---|---|
| 需求到断言的审查 | 为断言标记需求出处，移除无依据限制，补足规定结果 | 冻结义务，允许改写断言表达；正负样本验证 | 首轮；模型可能误删真实要求 |
| 对象作用域与语义定位 | 先锁定唯一业务对象，再找内部动作；从真实 DOM 提取候选 | 要求名称、身份、作用域和唯一性，不靠任意 first() | 首轮；宽正则和 fallback 可能选错对象 |
| 多正确实现＋负例反馈修订 | 同一测试在多种开发实现执行，将误拒和漏检共同反馈 | 每轮保护已通过正样本及已检出负例 | 首轮主线；容易记忆开发样例，需独立族留出 |
| 用户动作适配器 | 在规格允许范围内为原生/自定义组件选择不同 UI 操作 | 指定入口与目标状态固定；不绕过 Close 等待测动作 | 出现动作不兼容时加入；维护成本和副作用 |
| 业务结果提取与关系断言 | 提取对象身份、内容、集合变化和重载后的状态 | 结果相等、非目标对象保持等条件必须有需求依据 | 出现结构绑定时加入；提取器本身可能出错 |
| 运行时文本 DOM / VLM 适配 | 固定规则失败后，文本模型选择实际元素；视觉义务再用 VLM | 只适配操作/证据收集，结果仍按固定义务检查 | 后续；运行成本、随机性、超预算和错误操作 |

数据隔离、固定时间、条件等待是所有方法的执行基础。将原始执行配置保留为诊断对照，避免把纯执行修复全部归因于语义泛化。

统一 data-testid 可作为“公开接口契约”方案，但需要实现者配合，改变了兼容范围；应另列接入要求和成本。当前上游已大量使用 role/name，简单替换定位 API 并不能自动扩大合规实现集合。

第一轮优先实施前三种机制，保留离线修订、最终纯 Playwright 执行的低成本特点。遇到已确认动作表达差异时加适配器；VLM 用于确实依赖视觉的义务或疑难案例。

## 9. 最小记录格式

每条结果至少包含：

`upstream_sha, requirement_id, scenario_ids, impl_family, stack, split, variant_id, parent_variant, reference_label, evidence_path, target_fault, method, generation_repeat, revision_round, test_hash, execution_repeat, result, failure_cause, target_reached, target_failure_confirmed, runtime_ms, model_usage`

参考标签与执行结果分表冻结。失败原因初步由模型建议，关键裁定按同一规则人工复核；不因知道方法组别而改变标准。

## 10. 相关依据与适用边界

- [Self-Refine](https://arxiv.org/abs/2303.17651)：提供生成—反馈—修订形式，不需要强化学习训练；不能直接证明该形式提升 ARC-Bench 泛化。
- [WebGen-Bench §3.2、§4.3](https://arxiv.org/html/2505.03733v1)：操作/期望结果及独立人工校验，可借鉴参考标签流程。
- [WebRISE](https://arxiv.org/html/2606.03220v1)：需求相关状态转换与动态 DOM 操作，可借鉴动作和判据分层；不直接引入其隐含产品约束。
- [Playwright locators](https://playwright.dev/docs/locators)：语义定位及显式测试契约的技术依据。
