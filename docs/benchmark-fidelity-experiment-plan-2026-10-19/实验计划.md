# ARC Bench 业务保真与界面适配实验计划

版本 1.0　日期 2026年10月19日　用途 评测器改进与工程验收

本实验的目标是让满足业务需求的实现能够被 ARC Bench 接受，同时继续拒绝违反需求的实现。优先改进评测器的界面识别、操作和结果观察；只有出现明确能力缺口时，才引入语义代理、视觉操作或替换浏览器执行框架。LLM 是否产生增益不是本实验的成功条件。

需要解决的矛盾是：固定组件、role/name 和页面结构可以帮助自动化执行，却可能把工具限制变成产品要求；删减操作或断言可以提高表面通过率，却可能遗漏业务义务。实验允许界面表达变化，保留需求的完整行为、结果和必要交互约束，并记录适配所需的人力、接入信息及运行成本。

先完成三个已知失败的诊断与修复，再在原材料上回归，最后用少量新界面进行验收。每一阶段均有明确交付和停止条件。执行者可直接从第 12 节开始。本文件提出的是后续工程实验；此前 cross-impl-generalization-v1 已结束，其历史结论和原始记录保持不变。

## 1 实验目标与边界

成功意味着评测器能执行完整场景、获得可信观察、依据业务义务作出判断。仅仅找到控件、增加通过数量，或让模型输出“成功”，都不足以证明目标达成。

本轮回答四个问题。第一，已知失败究竟属于实现缺陷、需求解释问题、界面绑定错误还是观察错误？第二，通用控件驱动能否解决这些问题，而不新增组件限制或删除业务检查？第三，对无法通用处理的界面，人工绑定、最小接入信息或语义识别分别需要多少代价？第四，是否存在更换执行框架才能解决的具体能力缺口？

默认范围仍是 Keep REQ-2.2、Keep REQ-4.1 和 BookStack REQ-6.4。结论限于被检查的业务场景与界面范围，不承诺接受任意界面，也不把需求本身有歧义的实现强行标为正确或错误。明确要求的可访问性、用户可发现性和视觉效果仍属于验收条件。

只改善自动化覆盖、尚未解决全部界面时，交付可包含受支持范围和需复核列表。需复核不能计作通过，也不能自动解释成业务错误。

## 2 现有证据与本轮变更

历史结论以 [已结束的 pilot 报告](../../experiments/cross-impl-generalization-v1/analysis/PILOT-REPORT.md) 为准。暂定标签下，M0L 接受封存正确单位 4/6，有效检出缺陷 8/12；M0 对应为 0/6、0/12。两轮共 36 次 qwen3-coder-next 调用未产生超过 M0L 的开发候选。所有 36 个材料标签仍待人工确认。

这些结果表明当前值得检查的是评测器的适配和观察能力。它们不能证明“三层架构单独导致提升”，也不能证明 LLM 或 Playwright 普遍有效或无效。M0 的缺陷原始拒绝率为 12/12；有效检出为零，是因为对应正确父本也被拒绝。

新实验不继续旧方案的多轮测试重写。它允许人工工程修复，以经过审查的需求为依据，比较不同界面接入方式。旧封存材料已经公开给执行者，本轮一律视为回归材料，不能再次称为未见实现。

创建新目录 `arc-bench/experiments/benchmark-fidelity-v2/` 保存新协议、修复与结果。该目录及本文中的新 runner 接口是待实现设计，不表示当前仓库已有对应脚本。旧实验目录仅作为只读来源；更正标签或解释时，在新目录保存带出处的修订记录，不覆盖旧报告。

## 3 先审查需求再修复测试

### 3.1 区分业务要求与测试接入要求

将所选需求的 ROOT、祖先节点、原子需求、场景、数据约定和必要前置流程逐条映射到义务。原文明确规定的组件或名称也要登记，但它们是否继续保留，需要依据产品目的重新判断，而不能仅因为原测试依赖它就继续保留。

表 1　需求条款的处理规则

| 类别 | 例子 | 本轮处理 |
| --- | --- | --- |
| 业务义务 | 关闭后自动保存且不丢内容 | 保留结果及必要操作约束 |
| 必要界面语义 | 能识别标签选择入口和目标对象 | 保留含义与可操作性 |
| 可变表达 | checkbox 或 chips，卡片或列表 | 允许经过核验的等价表达 |
| 自动化接入约定 | 固定 test ID 或绑定清单 | 单独登记成本，不冒充业务要求 |
| 未决条款 | “关闭”是否要求整个区域消失 | 裁决前不形成确定标签 |

新契约记为 B1。它从旧 S1 审计而来，逐项记录沿用、纠正、放宽和补充解释。每项变更必须写明原文、用户意图、保留义务、核验方式及受影响单位。修订解释可能改变旧单位标签，因此旧指标与 B1 指标不可直接混算。

不要为某个实现专门豁免业务要求。例如原文要求关闭即保存，就不能允许驱动额外点 Save；要求关键词高亮，就不能因为某组件难以提取而只检查文本存在。若决定改变产品要求，应作为独立的规格版本，不能算评测器修复。

### 3.2 重新审查判据中的界面假设

冻结判据发生在需求审查之后。已有 oracle 文件也可能包含错误假设，允许纠正，但须留下语义差异和回归证据。

“编辑器关闭”应先明确可观察含义：当前笔记的编辑交互已结束，相关编辑控件不再作为活动编辑界面呈现；可能仍保留外层布局或新建入口。若需求明确要求整个编辑区域消失，应按原要求核验。不能简单以某个推测出的祖先节点是否可见代替全部含义。

搜索场景中的准备操作与搜索义务分开记录。如果创建笔记本身失败，记录前置流程失败和搜索未完成，不能直接断言搜索算法错误。需要时增加独立的受控夹具测试来诊断搜索，但它只能补充测试，不能替代原本要求的完整 UI 场景。

### 3.3 人工核验材料标签

先按 [人工裁决包](../../experiments/cross-impl-generalization-v1/certification/ADJUDICATION-PACKET.md) 完成标签检查，优先处理 Cpilot-keep REQ-4.1 和 R1 至 R3。通过已有截图、动作日志及必要的交互复现，核对业务义务，而不是直接采纳原测试或另一个模型的结论。

正确单位需逐项满足 B1 义务。缺陷单位需有明确目标义务、能复现的违约证据，以及经确认正确的父本。若父本被改判为有缺陷，其配对先置为未决，不得继续把该配对当作有效负例。修复产品会产生新的材料版本，须重新核验。

由执行者完成初审，另一位人工复核者确认争议和验收材料。若暂时只有一人，可以推进工程诊断，但保留单人核验标记，不宣称已经独立验证。未决材料继续出现在材料账本中，并披露其对目标覆盖的影响。

## 4 三个必须解释的复现案例

表 2　首轮诊断任务

| 案例 | 已知症状 | 需要验证的机制 | 修复证据 |
| --- | --- | --- | --- |
| B-keep REQ-4.1 | 标签选项无法适配 | 对象识别、选项作用域、组件操作方式 | 目标标签确实选中且过滤正确 |
| Dpilot-bookstack REQ-6.4 | Tags 字段无法适配 | 字段含义与输入方式是否可由用户识别 | 正确填入标签且后续页面场景完成 |
| Cpilot-keep REQ-4.1 | 关闭后报告编辑器仍显示 | 真实未关闭、祖先误绑定或状态观察错误 | 动作前后证据与人工结论一致 |

每个案例执行同一诊断顺序：确认产品版本与标签；由人完成场景并记录可观察行为；回放原测试定位失败步骤；检查绑定、动作、观察和判据的输入输出；形成最小可复现记录；只修改承担错误的层；回放正确父本与对应缺陷。

人工也无法操作或结果确实错误时，不通过增加适配代码强行放行。存在多个同名控件时，应利用业务对象和作用域消歧，不使用任意 first/nth 选择来获取偶然通过。前置动作失败与目标义务失败分别归因。

三个案例的完成标准是“机制已确认且处理合理”，不预设三个暂定正确实现必须全部通过。若其中有真实缺陷，继续拒绝并提供证据就是正确处理。

## 5 评测器的实现方案

### 5.1 业务场景与界面驱动分开

将执行链定义为：完整业务场景 → 语义操作 → 界面绑定与控件驱动 → 浏览器操作 → 有来源的观察值 → 业务判据。业务场景不直接依赖具体组件库。

建议能力接口包括 openNoteEditor、enterNoteContent、dismissNoteEditor、selectLabel、searchNotes、openPage、readVisibleNotes 和 readEditorFields。它们是拟实现的项目接口，不是 Playwright 或第三方 SDK 的现成 API。

控件驱动至少覆盖原生文本输入与 contenteditable、原生选择与自定义选项、chips 增删、卡片与列表记录、弹窗与内联编辑。驱动根据已识别的控件特征选择动作，不根据实现家族 ID、缺陷 ID 或预期成绩分支。允许为明确支持的实现编写专用绑定，但须归入 H 路线并记录维护成本。

操作日志记录要执行的业务意图、目标对象、实际控件、动作及前后证据。自动化只能执行场景允许的动作。禁止为自动保存补点 Save、用后端写入替代 UI 创建、失败后偷偷重建对象，或通过多次重复点击直到出现期望结果。

### 5.2 观察值必须可追溯

观察器返回原始值和来源，不返回“已经符合预期”的自我判断。每项观察至少关联业务对象、字段、DOM 或截图位置、采集时间及确定性状态。模型提取的 JSON 满足 schema，不等于事实正确。

例如搜索结果应提取当前结果集合中各条记录的身份、标题和正文片段，再与期望集合比较；不能仅在整页搜索关键词。正文可能存在于编辑区、隐藏模板或旁边另一条记录中，必须校验对象归属与用户可见性。

对于高亮、换行或遮挡等视觉义务，可以结合 DOM、计算样式与截图。不得把某个 class 名、mark 标签或任意 CSS 阈值直接当成需求本身。首轮采用人工审定的明确视觉样例；无法自动可靠判断的样例进入复核，而不是删除该义务。

若有评测方控制的后端或存储，可增加只读核验来确认持久化及对象数量。它不代替 UI 的可见结果，也不能由被测应用自行返回一个“满足要求”的布尔值。没有可信后端接口时不强加这一依赖。

### 5.3 观察错误也要有专门回归

为观察器准备干扰样例：页面其他区域出现同样文字、相邻对象包含关键词、隐藏模板包含完整答案、编辑器外壳保留但活动控件已关闭，以及同名动作同时存在。这些是评测器自测，不都属于产品业务缺陷。

正确表达回归与业务缺陷回归分别保存。第一类证明不能因换组件而失败；第二类证明修复没有删减判据。另用错误绑定和错读对象样例检查接入协议是否可能让评测器读取伪证据。

## 6 比较路线与允许的信息

表 3　候选路线及比较范围

| 标识 | 方案 | 可用信息与成本 | 用途 |
| --- | --- | --- | --- |
| B | 对齐 B1 的旧 M0L | 原适配策略，共用新场景与判据 | 主基线 |
| D | 通用能力接口与控件驱动 | 公开需求、开发 UI 和开发反馈 | 默认工程方案 |
| H | 人工界面绑定 | 人工查看每套 UI，记录绑定工时 | 可操作性参照与部署备选 |
| S | 语义识别辅助绑定 | 运行时 DOM 或截图，固定模型和预算 | D 无法覆盖时的候选 |
| V | 视觉操作或替代执行器 | 同等任务与可用证据，增加执行通道 | 明确能力缺口的专项候选 |

旧 M0、旧 M0L 作为历史诊断保留；它们在旧协议上的数字不与 B1 直接排名。B 只做必要的契约、共同输入和日志接口对齐，保留原定位与观察策略；每项共同修改列出差异。D 相对 B 的收益才用于判断新驱动的工程效果。如果必须修改某个观察规则以纠正原 oracle 的含义，先确定其属于共同契约修复还是 D 的观察实现改进，再冻结比较边界。

本轮先实现 B 和 D，不要求实现所有路线。H 用于回答“人能否明确绑定，并在完整判据下完成该场景”。H 的实现专用绑定可以随应用维护，但不能称为零接入的自动泛化；每个实现的制作和更新成本都要列出。

### 6.1 最小接入协议作为独立选择

H 首选评测侧绑定文件，仅描述 UI 上的目标和控件类型，不修改产品。另一种选择是实现提供业务语义标记或绑定清单，记为 H-hook；必须与 H 分开报告。标记可以指出 note.create、note.content 或记录身份，但不能规定 UI 必须使用按钮、某种编辑器或特定文案。

H-hook 仍是接入要求。将它放在独立的评测接入文档，并记录添加工作量；不能宣称移除了全部约束。标记只能指向真实可见、可操作的界面和实际观察来源。错误标记、隐藏答案节点或绕过 UI 的行为不得计作通过。

部署时是否允许人工绑定或 H-hook，由所选 benchmark 模式明确决定。本轮默认主路线 D 不要求应用添加标记，因此不会通过隐藏新增接入条件换取通过率。

### 6.2 模型仅参与界面识别

只有 D 存在已经确认的识别缺口时才试 S。给模型当前 UI、要识别的业务概念和允许操作；返回目标定位、控件类型或有来源的观察。不给它修改业务判据、跳过场景或读取标签的权限。

优先在准备阶段生成并检查绑定，按应用构建版本缓存，评分阶段使用冻结绑定。动态列表仍通过运行时业务对象身份定位；构建版本或 UI 状态不匹配时显式报错。若必须运行时重新识别，预先固定调用次数和触发规则，完整保存输出，不得按测试成败不断尝试直到通过。

对于受控父本和缺陷版本，尽可能沿用同一绑定。若目标控件消失或含义被改变，不能让自修复代理换一条路径绕过缺陷。必要的重新识别应说明其寻找的是同一业务能力，并保留失败证据。目标缺陷是否被检出仍由独立规则确认。

Stagehand 的 observe、act、extract 可作为 S 的实现候选；它提供自然语言操作与结构化提取，但官方能力描述不是该方案适合 ARC Bench 的验证结果。锁定实际使用的版本、模型和返回格式后再试运行。[来源 3]

## 7 材料与验收划分

### 7.1 旧材料作为开放回归集

原 pilot 计划有 12 个正确单位和 24 个注入缺陷单位，共 36 个。先按 B1 重新核验。真实数量以确认结果为准，未决项不能静默排除。它们全部允许用于诊断与开发，所有方法共享确认后的标签与证据。

评价单位为“需求 × 实现版本 × 变体”。同一根应用下的多个需求相关，不能把它们视为独立软件。单位通过意味着全部必测场景完成并满足义务。

### 7.2 新增少量界面变体

目标新增 12 个正确单位，每条需求 4 个；其中每条 2 个用于开发、2 个用于验收。每个正确单位构造 2 个单一业务缺陷版本，共 24 个缺陷单位。由此新增开发集为 6 正确加 12 缺陷，验收集同样为 6 正确加 12 缺陷。

新增范围优先覆盖表 4。每个正确变体优先只改变一个界面维度，记录与父实现的关系。它们可以是旧应用的受控变体，但此时只能支持对新表达的验收，不能声称跨独立实现或跨未知框架泛化。真正换技术栈必须另有独立实现与核验。

表 4　新表达与对应业务错误

| 需求 | 正确表达候选 | 必须继续拒绝的错误 |
| --- | --- | --- |
| Keep REQ-2.2 | 内联与弹窗编辑，富文本与原生输入，外壳保留 | 需要额外保存、丢失一行、重复创建、刷新丢失 |
| Keep REQ-4.1 | 菜单、chips、不同选项控件，卡片或表格结果 | 只搜标题、过滤对象错误、清空不恢复、高亮缺失 |
| BookStack REQ-6.4 | 字段标签变化、标签录入方式变化、不同正文编辑器 | 打开错误页面、预填错内容、串页或内容不完整 |

每条需求的 4 个正确单位各配 2 个缺陷，在该需求内轮换错误类别。表中为候选机制，具体义务和有效性需独立核验。每个新增或修改的关键判据至少要有一个针对性负例；若 24 个缺陷不足覆盖，补充并在运行前更新预算。

验收材料应由未参与驱动调试的人准备并保管具体 UI。只提前公开变更维度和业务范围，不公开具体绑定。只有一名执行者时，改称“冻结后的回归验收”，记录其暴露情况，不包装成盲测。

### 7.3 冻结与修改规则

验收前冻结 B1、标签、样本列表、场景输入、候选代码、适配来源、模型配置和运行预算。验收期间不修改候选或判据。发现新问题后可进入下一次工程修复，但该批材料随后成为开发回归集；下一轮要证明新表达能力，应另加未用于修订的验收材料。

这是一项工程迭代规则，不要求一次试验就解决全部 UI。每轮报告修复了什么、仍不支持什么和增加了多少成本。

## 8 执行流程与运行配置

表 5　分阶段操作与出口

| 阶段 | 执行内容 | 出口 |
| --- | --- | --- |
| P0 | B1 审计、标签裁决、旧材料快照 | 关键歧义解决，来源与版本可追溯 |
| P1 | 三案例诊断，H 验证可操作性 | 区分产品问题与评测器问题 |
| P2 | 实现 B 与 D，旧材料及新开发集回归 | 完整义务覆盖，无已知缺陷放行 |
| P3 | 冻结后运行新验收集 | 决定发布、限定支持或继续修复 |
| P4 | 按缺口试 S 或 V | 判断新增能力是否值得其成本 |

浏览器与依赖使用旧 pilot 的确切安装版本和锁文件作为起点，记录 Node、Playwright、浏览器构建、操作系统、时区与视口。不要在实验过程中无记录升级。接入 S 或 V 时单独锁定其依赖；若它只支持某种浏览器，就在共同支持的浏览器上比较，并单列兼容范围。

同一场景所有路线使用相同的初始数据、输入、种子和义务。每个单位运行 3 次，每次独立重置浏览器上下文和应用状态。默认 workers=1、retries=0；case 总预算 120 秒，action 15 秒、navigation 30 秒、expect 10 秒。已有业务规定的等待窗应在冻结前逐项确认并统一配置。语义调用时间计入运行预算。

先做服务健康检查，再执行完整场景。外部基础设施故障最多修复后重跑 2 次，保留全部尝试；定位超时、模型选错对象、测试代码错误和产品崩溃不按基础设施故障洗掉。方法与目标顺序配对随机化。

从 Playwright JSON reporter 读取 case 清单与最终状态，不解析 stdout 第一条 passed。零 case、漏场景、skip、only 和重复 case 视为执行协议错误。三次中任何一次义务失败，该单位都不计稳定接受。

H 的人工准备工时与运行时间分开记录；不能只比较准备完成后的秒数。S 记录准备阶段及运行阶段全部调用。对 S 的重复运行，声明绑定是否缓存；冷启动发现与缓存回放分开报告。

## 9 结果状态与指标

### 9.1 失败原因不能由超时自动推断

表 6　结果状态

| 状态 | 判定依据 | 对评测的含义 |
| --- | --- | --- |
| PASS | 全部场景与义务有证据通过 | 可接受 |
| REQUIREMENT_FAIL | 有证据违反指定义务 | 业务不符合 |
| ADAPTATION_UNKNOWN | 无法可靠定位、操作或提取 | 未完成评测，需适配或复核 |
| TEST_ERROR | 评测器语法或执行逻辑错误 | 未完成评测，修评测器 |
| POLICY_INVALID | 绕过 UI、跳过义务、读标签等 | 候选无效 |
| INFRA_UNKNOWN | 外部运行条件未恢复 | 未完成评测，保留缺失信息 |

找不到目标可能是定位器不足，也可能是产品确实没有必要功能。只有独立证据确认目标业务能力缺失或违约时，才能记 REQUIREMENT_FAIL。不得把所有 ADAPTATION_UNKNOWN 都归成实现错误，也不得通过这个状态隐藏真实缺陷。

每次结果保存目标义务、最后完成的步骤、是否到达目标、实际观察、证据路径及归因者。业务失败的证据不必全部来自最终断言，但必须与目标缺陷有因果关联；无关登录失败不能算检出了正文保存缺陷。

### 9.2 主指标

令 C 为人工确认的正确单位集合，M 为有效父本与缺陷配对集合。A(T,c)=1 表示方法 T 在 c 上三次全部 PASS；D(T,m)=1 表示在 m 上三次都确认了目标义务违约。

CAR@3 = Σ A(T,c) / |C|。

EDR@3 = Σ [A(T,parent(m)) × D(T,m)] / |M|。

同时报告每个需求、每种界面维度的 k/n，再给需求等权平均。固定分母由材料核验决定，不能因为某方法不接受父本就缩小缺陷分母。EDR 增加可能来自父本恢复，所以另报两方法都接受父本的共同配对子集检出情况。

错误放行单独报告：任一次运行将已确认缺陷记为 PASS 的单位数和运行次数。发布检查不允许用三次投票掩盖一次错误放行。缺陷上的未知或工具错误也不算有效检出。

### 9.3 需求覆盖与稳定性

建立“条款 → 场景 → 观察 → 判据 → 负例”映射。结构覆盖要求所有必测条款都有映射；执行覆盖记录实际取得证据并运行判据的义务次数，占计划次数的比例。仅存在 assertion 代码不能证明覆盖充分，实际读取错误对象也不能算有效观察。

对正确单位报告各义务的执行覆盖；对缺陷单位报告目标义务到达和检出，区分前置阻断。若采用 fail-fast，未执行的后续义务仍计为未覆盖，不推测它们通过。为视觉义务单列自动完成和人工复核比例。

稳定性报告三次结果是否一致，以及 PASS 与非 PASS 的翻转单位数；另列业务失败、适配未知、工具错误和外部未知的转移。三次全部未知虽稳定，仍不代表评测有效。拟发布方案在最终验收集上做总计 K=10 的复跑，原有 3 次计入 10 次。

适配未知和测试错误保留在固定分母中，当前方法的 CAR 和 EDR 均不因此获得分数；它们已经暴露评测器能力不足，不能按“可能成功”提高能力估计。只有外部基础设施导致未完成的运行，另给缺失假设下的保守下界与可能上界。已有一次确定失败的正确单位，不得因另一次外部未知而加入 CAR@3 上界。标签本身未决的单位另列数量和占计划样本比例，必要时做标签假设下的敏感性表；不能只公布已完成部分的漂亮百分比。

### 9.4 成本与结论边界

记录每个需求和每套实现的驱动开发、人工绑定、标记接入、核验、维护工时，以及模型调用、实际 token、费用、运行中位数和 P95。初次开发与后续新增实现的边际成本分开记录。

样本规模小且许多材料来自同一根实现，报告逐例变化、k/n 和成本即可。重复运行不是独立软件样本，不做夸大的总体显著性推断。注入缺陷结果不能替代自然缺陷表现。

## 10 接受方案与更换框架的条件

### 10.1 工程发布条件

拟发布的支持范围必须逐项说明。三个已知案例均需完成可信诊断；确认正确且处于支持范围的案例应三次通过，真实有缺陷的案例应正确拒绝，未决情况不可包装成已修好。

默认验收目标是：新验收集 6 个确认正确单位全部稳定接受，12 个有效缺陷配对全部稳定有效检出；全部必测义务有可信证据；没有新错误放行、越权动作或跳过；最终 K=10 不发生状态翻转。标签或配对数量变化时使用冻结后的实际 k/n，任何目标调整必须发生在看成绩之前。

在全部确认回归材料上，候选不得丢失 B 已有的稳定接受与目标缺陷检出。相对 B 必须恢复至少一个经确认的适配失败，或在覆盖相同的条件下减少接入限制或维护成本；否则不能声称改进有效。前者按实例报告，后者须有接入条款和工时证据。

该门槛是小规模工程验收标准，不证明无限制泛化。未达到时可以发布范围更窄的版本，但需明确支持列表、失败原因和人工复核流程；不得把未知改成通过来满足门槛。

### 10.2 启用语义识别的条件

若人能明确完成任务，D 仍因名称、结构或语境识别失败，而可复用驱动已无法在合理工作量内解决，可试 S。建议开发预算为每类失败最多 4 小时诊断与通用修复；超过后先说明缺口，再决定是否扩大投入，不无限追加别名。

先在已公开的失败样例上验证 S 是否找到正确对象。S 仍必须通过同一完整场景与缺陷检查。若只是增加模型调用却未减少未知，或引入错误对象操作，应停止该路线。模型只通过一个演示不构成替代 D 的依据。

### 10.3 更换执行框架的条件

换框架前提交最小复现：用户可完成的操作、当前驱动无法完成的具体步骤、已尝试的标准能力、替代工具的完整执行证据，以及对缺陷检出的影响。普通名称不匹配或观察规则错误，优先修复绑定与观察。

Playwright 已支持多种定位及输入方式；换为 Selenium 或 Cypress 仍需建立业务语义到控件的映射。因此，不以“换框架可能更智能”作为迁移理由。[来源 1、2、4、5]

当 DOM 没有提供足够交互信息、界面主要由 Canvas 绘制，或任务涉及浏览器外原生 UI 时，可评估视觉通道或新的执行器。这是待验证的选项，不预设它更准确。先替换失败能力的驱动，保留场景、判据和日志接口，避免一次重写整个 benchmark。

替代方案至少应恢复一个已确认的能力缺口，满足相同的正确与缺陷回归，并披露模型成本、运行波动、浏览器支持范围和人工介入。只有在这些条件满足且维护代价可接受时才迁移。若结果证据仍不可靠，换执行器也不能解决观察问题。

## 11 时间预算与运行规模

表 7　默认工作量估计

| 工作包 | 人工工时 | 交付 |
| --- | --- | --- |
| 需求与旧标签审查 | 6 至 10 小时 | B1、裁决记录、材料账本 |
| 三案例诊断与驱动修复 | 12 至 18 小时 | B、D、最小复现与回归 |
| 新变体和缺陷制作核验 | 18 至 30 小时 | 12 个正确与 24 个缺陷单位 |
| 冻结验收与报告 | 8 至 16 小时 | 逐例结果、费用、部署建议 |

核心工作预计 44 至 74 人时，建议分布在 8 至 13 个工作日，另预留约 20% 复核和返工。多人工作按实际累计人时记录。S 或 V 的专项原型另给 12 至 24 人时上限；无法在预算内澄清能力收益时先停止扩展。

若旧材料 36 个全部有效，加新增 36 个，总计 72 个目标。B 和 D 各运行 3 次，共 72 × 2 × 3 = 432 次需求级执行。其中开发回归 54 个目标对应 324 次，验收 18 个目标对应 108 次。一次需求级执行包含该需求全部场景，不等于一个 Playwright case。

拟发布方案在 18 个验收目标上从 K=3 增至 K=10，额外 18 × 7 = 126 次。核心预计 558 次，不含人工核验、开发中间版本、基础设施重跑和新增负例。每新增一种方法完整运行 72 个目标的 K=3 矩阵，增加 216 次；仅做 18 个验收目标则增加 54 次，报告必须说明覆盖范围。

运行机时用首批实测的平均需求耗时 t 秒估算 N×t/3600，再加启动和重置成本。默认 B、D 和人工 H 不要求模型调用。可选 S 初次探索建议上限 200 次调用、每次输入 8k 与输出 1k token；图像、推理 token 和供应商限制单独记录。运行前填写模型、实际价格与总费用上限，不沿用旧 NUS 调用预计免费的假设。

若预算不足，优先完成三个案例、旧材料回归和完整业务负例，推迟新表达验收或 S/V。此时交付称为工程修复，不宣称已完成新的兼容范围验证。

## 12 第一周执行清单

第一天：创建新实验目录和只读来源快照；登记旧报告、原实现、测试与依赖 hash；复制标签为新账本；完成三个失败的人工复现；开始逐项核对 B1。第一天产物是失败归因和待裁决项，不是提高通过率的补丁数量。

第二天：完成关键歧义裁决，确认三例究竟哪些是正确实现；固定完整场景与义务映射；建立 B；手工绑定能够操作的 UI，验证可操作性参照；明确 D 需要补哪些控件能力。尚未确认标签的材料可以诊断，不能进入确定性成绩。

第三至四天：实现 D 的最小驱动和观察证据；每修一个问题立即检查对应父本、目标缺陷及错读对象样例；回放完整需求。记录是否增加了实现专用分支，若增加则归入 H，不混入 D。

第五天：汇总旧材料回归；确认业务检查没有减少；冻结新增界面维度与缺陷计划；由复核者准备或保管新验收材料。如果 D 已解决主要问题，继续完成新验收，不必为使用 LLM 而另造任务。若存在明确能力缺口，再填写 S/V 试验卡。

## 13 结果报告与交付

主表按方法报告信息来源、接入条件、CAR@3、EDR@3、错误放行、义务执行覆盖、未知数量、状态翻转、人工工时和运行成本。H、H-hook 与 D/S 分组，避免把更多人工或应用配合当成免费收益。

每个修复案例展示需求条款、正确行为、原失败证据、责任层、修复差异、父本恢复及目标缺陷仍被检出的证据。对未修复项写明是产品错误、规格歧义、缺少绑定还是缺少观察能力。

报告结论围绕部署选择：保留 Playwright 并改进驱动；采用人工绑定以支持确定实现；增加语义或视觉通道；或替换某项执行能力。选择理由应包括覆盖、误判风险和维护成本，不能只依据总通过率。

交付包包含 B1 与变更记录、人工标签与争议裁决、已支持界面范围、驱动与绑定、完整业务回归、原始日志、费用和限制说明。旧实验结论保持原样，新结果注明使用的契约和材料版本。

## 附录 C 执行前复核

1. 目标是否仍是 bench 忠实验收需求？确认没有把 LLM 增益设为继续的必要条件。
2. 是否保留全部业务义务？逐条核对规范映射、场景、观察和针对负例；检查原 oracle 中隐含的 UI 假设。
3. 标签与证据是否可信？解决关键争议，记录独立复核和未决材料，避免用被改进测试给自己认证。
4. 比较是否公平？区分同契约比较与历史参考，区分通用驱动、人工绑定和应用标记，并披露准备成本。

资料 B　[旧人工裁决包](../../experiments/cross-impl-generalization-v1/certification/ADJUDICATION-PACKET.md) 与 [旧规格审计](../../experiments/cross-impl-generalization-v1/protocol/spec-audit-pilot.md)。用于开始 B1 审查，不作为人工核验已经完成的证明。

资料 C　[现有操作层](../../experiments/cross-impl-generalization-v1/methods/M0L/keep/tests/lib/operations.ts) 与 [观察层](../../experiments/cross-impl-generalization-v1/methods/M0L/keep/tests/lib/observe.ts)。名称枚举、祖先推断及容器可见性检查是本轮诊断依据，尚不能单凭源码判定具体材料谁对谁错。

来源 1　[Playwright Locators](https://playwright.dev/docs/locators)。多种定位方式、显式测试接口和定位范围。固定 role/name 不是唯一选择。

来源 2　[Playwright Actions](https://playwright.dev/docs/input)。原生输入、contenteditable 和其他用户交互能力。

来源 3　[Stagehand Introduction](https://docs.stagehand.dev/v4/first-steps/introduction)。语义操作、发现和提取的候选能力；是否满足本实验需要仍须验证。

来源 4　[Selenium Locator Strategies](https://www.selenium.dev/documentation/webdriver/elements/locators/)。更换传统浏览器自动化框架仍需定位元素。

来源 5　[Cypress Best Practices](https://docs.cypress.io/app/core-concepts/best-practices)。测试属性与业务文本的选择应依据测试意图。

上述官方资料在 2026年10月19日查阅。工具文档会更新，执行时以冻结的具体版本为准；本文不把产品能力介绍当成实验效果证据。
