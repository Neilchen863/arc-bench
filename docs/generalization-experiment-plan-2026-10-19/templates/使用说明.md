# 实验记录模板使用说明

这些文件供执行实验时复制填写，所有 null 和 DRAFT 状态都表示尚未填写或核验，不是实验结果。脚本应拒绝将未冻结配置用于正式封存评价。

1. 复制 protocol.template.json 为新实验目录的 protocol/protocol.json，填写执行负责人、模型快照、技术栈版本、组件库、完整场景映射、输入种子、判据 hash、关键缺陷 ID 和访问隔离安排。v1.1 主实验是 S1，S0 是现有约定的兼容性参照，不是最优界面设计的默认答案。
2. 为每个需求—实现—变体填写 material-and-certification.template.json。相同应用根实现下的不同需求可复用启动信息，但必须独立记录义务认证。正确父本与每个缺陷各占一个单位。
3. 用独立核验流程完成 reference_repeats 和 evidence_paths；完成复核后才能将 UNDETERMINED 改成 SATISFIED 或 VIOLATED。
4. 每次候选运行复制 run-record.template.json。run结果与reference标签分别保存，避免由候选成败回写正确性标签。
5. 用 interface-relaxation.template.json 逐条记录 S0 到 S1 的变更。先冻结业务不变量、可变表达和认证规则，再构建主实验材料，不能看到候选成绩后才增补例外。材料同时登记 S0 与 S1 标签，并提前冻结 S0 兼容子集。
6. 实验目录、脚本和汇总程序按主计划第11节实现。模板不提供已存在的 run_matrix 或 score 命令。

pilot 目标为12个正确单位、24个缺陷单位，6套候选系统在封存18目标上各重复3次，共324次需求级执行。正式目标为36个正确单位、108个缺陷单位，14套候选系统在封存48目标上各重复3次，共2016次需求级执行。这里不含认证、开发、验证、消融和基础设施重跑。

M0L 为获得完整 S1 的静态通用适配与分层契约基线；M1–M4 使用相同场景输入和固定业务判据。主比较为 M2 对 M0L，M0 原测试作为历史参考。所有候选生成完后，统一按冻结的 M0L 保护清单选择。M3 不得接收任何新的执行结果、编译错误、接受位或根据成绩选择的编辑基底。
