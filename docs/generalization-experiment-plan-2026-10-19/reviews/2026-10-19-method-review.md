## 主要问题

### MAJOR-1 原始 M0 与新判据、新场景覆盖混杂

**位置与原文：** §7.1 第 212 行规定 M0“原 spec 和 helpers 不改”；§6.3 第 196 行冻结新判据核心；§7.1 第 216 行只规定 M1/M2 共享核心；§9.3 第 337 行把 M2 对 M0 设为主比较。

**证据与影响：** 原 BookStack `REQ-6.4.spec.ts` 的每个 case 只创建一篇页面，而 §3.1 要求创建两篇并选择非第一篇。这是合理的辨识输入，但从 M0 到新方法已经同时改变输入覆盖和判据实现。接受或检出改善不能全部归因于多实现反馈或多轮修订。即使所有新方法遵守相同义务，机械重写原 oracle、增加对象辨识输入也可能独自产生收益。

**最小修正：** 保留 M0 作为端到端原工具对照；增加冻结的 M0L，采用与所有生成组完全相同的场景输入、Observation schema、core、执行配置，仅用按原选择器/提取假设机械迁移的操作层和观察层。M0L 不使用新增实现执行反馈修复适配，迁移差异逐项审计。候选起点、回退与保护基线统一为 M0L。分别报告 M0→M0L 的契约工程收益、M0L→M2 的自动修订增量，以及 M1/M3/M4 对照。若不加该基线，须明确将 M2 对 M0 降为整个组合流程的实用效果，不作反馈机制解释。

**严重性：major；置信度：高。** 作者已接受增加 M0L；还需明确相同场景输入，而不仅是相同 core。

### MAJOR-2 pilot 暴露 Svelte 与正式“未见框架”互相矛盾

**位置与原文：** §4.1 表 4 第 118 行 F 为“Svelte…未见前端框架”；第 120 行将 Dpilot 指定为 Svelte，并允许开封后形成修订知识。

**证据与影响：** 新建 F 的源码只能恢复“未见根实现”，不能让方法开发阶段已见的框架变回未见。独立会话或不同控件库同样不能消除开发者从 pilot 学到的 Svelte 结构和适配规则。

**最小修正：** pilot 仅使用 React/Vue 的新根实现，Svelte 首次出现只在正式封存 F；或者将 F 改为暴露台账中从未使用的另一框架。若保留初稿安排，则所有相关结论改为“已见框架上的未见实现”，不再报告未知框架迁移。

**严重性：major；置信度：高。** 作者已接受 pilot 改 React/Vue，Svelte 留给正式 F；最终须检查模板、builder 输入和调试实例也未暴露 F。

### MAJOR-3 M3 可能间接收到新反馈，M4 的选择策略又不同

**位置与原文：** §7.2 第 224 行称 M3“无新增执行反馈”；§7.3 第 240 行规定只有已接受候选成为后续编辑基底；§7.4 第 248 行明确“M2/M3 的连续接受规则”且 M4 每个候选只对固定 M0 做保护。

**证据与影响：** 如果下一轮 M3 看到的是经运行筛选的已接受补丁，执行结果已经通过“选择哪份代码继续编辑”传入模型。不给完整报告不等于不给新增执行信息。另一个问题是 M2 必须保护沿途所有已获得收益，M4 只需不退化于初始基线，最终可选集合不同。M2 对 M4 的差异因此包含选择算法差异，不能干净解释为迭代优于独立采样。

**最小修正：** M2/M3 都按预定、与执行结果无关的链路从前一轮合法候选继续；仅 M2 在轮间得到新执行报告。生成完成后，M1–M4 全部候选采用同一固定基线保护清单和同一最终排序。若要保留 M2 的动态接受策略，应把它单独列为策略消融；M3 若收到接受位信息，应准确改名为“仅接受位反馈”，并另设真正盲修订对照。不要把这一差异只放在结果局限里而仍作单因素机制解释。

**严重性：major；置信度：高。** 已向作者报告，待修订核验。

## 中等及次要问题

### MODERATE-1 首轮配对不能是可选项，预算匹配范围需写清

§7.1 第 216 行是“首轮可以配对”，§7.2 第 222 行又称所有组候选数量相同，但 M1 只有一轮，M2–M4 最多三轮。若 M1 与 M2 首轮独立采样，M2−M1 包含首轮运气，不纯是追加修订收益。

**修正：** 对每个需求和生成重复，M1/M2 必须共用同一首轮 hash；M3 可以共享该首轮以提高配对效率，随后分叉。准确表述为 M2/M3/M4 预算上限匹配，M1 是低预算的一轮参照。日志区分逻辑候选数、实际模型调用和复用的执行结果；原 180 次仅是未复用情况下的保守上界，不是必需调用数。预先写明重复结果能否缓存复用及缓存键。

**严重性：moderate；置信度：高。**

### MODERATE-2 pilot 没有验证集，但通用算法仍无条件要求验证

§3.1 明确 pilot 无独立验证集；§7.3 步骤 6 却无阶段限定地要求先过验证再封存。这会让执行者临时选择跳过、挪用封存或自建小验证集。

**修正：** 明确 pilot 的步骤 6 为“开发选优后直接冻结并一次开封”，正式阶段才使用 D 的验证门槛。pilot 的保护规则仍在开发集执行，不把 pilot 留出用于挑候选。

**严重性：moderate；置信度：高。**

### MODERATE-3 命令是静态核对，不是已证明真实运行成功

§14 第 465 行“这组命令只证明原始安装和精确 spec 入口可运行”比现有证据强。所核对的源脚本确实生成 `test:e2e: playwright test`、把 URL 写入 config、安装 1.57.0 并导出 URL；复制 tests 和 source 调用从代码上合理。但实际安装、应用服务可达和 BookStack 前置流程未运行。

**修正：** 写为“命令已按固定提交静态核对，实际执行后用于检查安装与精确 spec 入口；尚未完成真实应用 smoke test”。执行阶段保存 `--list` 的两个 case、真实运行 JSON 和 exit status，再更新状态。不要额外编造已跑过的证据。

**严重性：moderate；置信度：高。**

## 冻结前必须明确的问题

1. M0L 与 M1–M4 是否使用逐字相同的场景数据构造与只读 core？M0→M0L 的每项变化如何审计？
2. M3 的下一轮上下文和编辑基底是否完全不依赖新执行结果？M2–M4 是否共享最终选择算法？
3. 首轮到底共享哪些方法、哪些 hash？复用调用及执行如何计费、如何计数？
4. pilot 与正式验证步骤是否分别写成无歧义流程？Svelte 与未见组件库是否在所有 pilot 调试中保持未暴露？
5. 最终协议是否已填实际框架/组件库版本、模型快照、seed 规则、预期 case ID、输入分区、运行预算和关键缺陷清单？

这些是执行者在冻结文件中需要回答的字段，不要求在本次文档交付时额外征求用户许可。

## 修订优先级

1. **运行任何方法前：** 修正框架划分；加入 M0L 或收窄归因；统一候选选择；关闭 M3 的隐式反馈通道。
2. **冻结方法前：** 强制首轮配对；区分 pilot/正式验证；明确实际预算和保守上限；同步运行矩阵与结果表。
3. **启动大矩阵前：** 用两个 BookStack 开发实现执行 smoke test，核对两个 case、固定分母、三次重置、永远 PASS/FAIL 控制及目标缺陷归因；保留结果，别以静态读脚本替代。
4. **形成结论前：** 逐项报告原始 M0、M0L 与自动修订增量；自然缺陷不足就收窄真实 bug 结论；不要用两个封存家族推断任意框架。
