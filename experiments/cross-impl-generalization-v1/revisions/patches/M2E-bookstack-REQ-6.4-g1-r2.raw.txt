## Analysis of Dev Feedback

### Failure Patterns
1. **B64-D1 failures (both units A and B)**:  
   - `read_selected_page` and `reopen_page_editor` fail at `B64-O1`  
   - **Root cause**: The opened page heading is *Page A* instead of *Page B (TARGET)*  
   - **Evidence**: aria snapshots show `<heading "Page A 6.4.x ...">` as H1, not the target page  
   - **Interpretation**: `openPage` is clicking the *first* page entry (Page A) instead of the TARGET page  
   - **Why?** `listEntries` uses `exact: true` for role=link/button, but the page list likely contains *multiple* entries with the same visible title due to test isolation suffixes, or the page list is not properly scoped.

2. **B64-D2 failures (both units A and B)**:  
   - `read_selected_page` passes, but `reopen_page_editor` fails at `B64-O5`  
   - **Root cause**: Editor body field is empty (`""`) instead of `target.body`  
   - **Evidence**: aria shows `textbox "Write your page content here..."` with no value  
   - **Interpretation**: The body field is a rich-text editor (contenteditable), but `readValue` uses `innerText` which may not capture content in some implementations.

### Key Observations from Aria Snapshots
- In B64-D1 failures:  
  - Breadcrumb shows `Page A 6.4.x` (not TARGET)  
  - Article heading is `Page A 6.4.x`  
  - This confirms `openPage` is selecting the wrong page entry.

- In B64-D2 failures:  
  - Editor title field has correct value (`Page B 6.4.x`)  
  - Body field (`textbox "Write your page content here..."`) has no text content  
  - This confirms body field is a rich editor, and `innerText` may not reflect its content.

### Root Cause Hypothesis
- **Page selection issue**: The `openPage` function uses `byRole('link', title)` or `byRole('button', title)` with `exact: true`.  
  - However, the page list likely contains *multiple* entries with the same base title (e.g., `Page B 6.4.1 [r1-w0-...]` appears only once, but the locator may be matching the *first* matching entry in the entire page, not the one in the page list).  
  - The `pageListScope` function returns a fallback to `page` if resolution fails, which could cause global search instead of scoped search.

- **Body field reading issue**:  
  - The body field is `textbox "Write your page content here..."` (placeholder), but in the editor it's likely a `contenteditable` div.  
  - `readValue` uses `innerText` for non-input elements, but if the editor uses a different structure (e.g., iframe, shadow DOM, or inner HTML), this may not capture the content.

---

## Patch

### 1. Fix `pageListScope` to be more robust and ensure scoped search
The current `pageListScope` has many fallbacks and may return `page` if resolution fails, causing unscoped search. We need to ensure the page list is correctly identified and scoped.

### 2. Fix `openPage` to use scoped search strictly
Ensure `openPage` uses the `pageListScope` locator strictly, not falling back to global search.

### 3. Fix `readValue` for rich editors
The body field is likely a `contenteditable` div. We need to ensure `innerText` works, or use `textContent`/`innerHTML` as fallback.

export async function readValue(field: Locator): Promise<string> {
  return field.evaluate(e => {
    if (e instanceof HTMLInputElement || e instanceof HTMLTextAreaElement) {
      return e.value;
    }
    // For contenteditable or rich editors, use textContent to capture all text.
    const el = e as HTMLElement;
    return el.textContent ?? '';
  });
